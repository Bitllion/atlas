## 1. 项目概述

### 1.1 项目介绍

Atlas 是一个面向 AI 基础设施供应商、服务商及其客户场景的资产生命周期和运营管理平台，覆盖 AI 数据中心、高性能计算环境以及企业级基础设施环境。

Atlas 通过建立统一的基础设施对象数字模型（Infrastructure Object Model），实现对以下内容的统一管理：

- IT 硬件资源
- 网络资源
- 机房基础设施
- 资产生命周期
- 运维流程
- 工作流与运营流程
- 知识沉淀

Atlas 的目标不是简单记录资产或控制设备，而是建立企业基础设施的数字化映射，使物理世界中的设备、关系、状态、权限和变化能够在数字系统中被准确表达和管理。

Atlas 必须支持这样的真实场景：资产属于企业，但部署在客户数据中心；客户拥有带内权限，企业可能没有 OS、网络或应用权限，只负责硬件维保；即使设备无法持续采集，资产生命周期仍然需要被管理。

### 2.3 机房基础设施

传统资产管理系统通常只能描述“我有什么设备”，但无法回答：

Atlas 旨在解决这些问题。

## 5. 核心设计理念

### 5.1 基础设施对象模型优先

Atlas 不以资产表作为核心，而以 `Infrastructure Object` 作为核心对象。任何基础设施实体都是一个对象，例如：

```yaml
Object:
  Type: SERVER
  Model: GB300
  Serial: xxxx
```

```yaml
Object:
  Type: GPU
  Model: B300
  Serial: xxxx
```

```yaml
Object:
  Type: CDU
  Model: xxxx
```

### 5.2 单一对象，多业务视角

同一个对象可以被不同业务使用。例如，GB300 服务器同时服务于：

- Asset：采购信息、供应商、合同
- Operations：故障记录、维修记录、巡检记录
- Workflow：审批、交付、维保和现场处理流程

### 5.3 所有权、使用权与管理范围分离

Atlas 不假设资产所有者、使用方、部署地点和实际管理方是同一主体。每个基础设施对象都应能表达：

- Ownership：资产所有权
- Usage：使用方或客户
- Location：实际部署地点
- Maintenance Responsibility：维保责任
- Management Scope：企业对该对象拥有的管理范围

示例：

```yaml
Management Scope:
  ownership: OWNED
  location: CUSTOMER_SITE
  operation_control: HARDWARE_ONLY
  access: NO_OS_ACCESS
  maintenance: RESPONSIBLE
```

典型管理范围包括：

| 场景 | 管理权限 | 可执行能力 |
| --- | --- | --- |
| 自有机房 | `FULL_CONTROL` | 采集、部署、修改 |
| 客户机房 | `MAINTENANCE_ONLY` | 资产管理、维保、故障处理 |

## 6. Atlas 核心模型

Atlas Core 包含五个基础模型。

### 6.1 Object Model

描述“它是什么”，例如：

- Server
- GPU
- NIC
- Rack
- CDU

### 6.2 Relationship Model

描述“它和谁有什么关系”，例如：

| 关系类型 | 示例 |
| --- | --- |
| 包含 | Rack `contains` Server |
| 组成 | Server `contains` GPU |
| 连接 | NIC `connected_to` Switch |
| 供冷 | CDU `feeds` Rack |

### 6.3 Specification Model

描述“它有什么技术参数”。

GPU 示例：

```yaml
Model: B300
Memory: 288GB
Firmware: 97.xx
UUID: xxxx
PCI BDF: 0000:41:00.0
```

BF3 网卡可包含：

- MAC
- Firmware
- PCI BDF
- Speed
- Protocol

CDU 可包含：

- Cooling Capacity
- Flow Rate
- Temperature
- Pump Status

### 6.4 Data Source Model

描述“数据来自哪里，以及我们能如何访问它”。数据模型不仅记录来源，还应记录 Access Capability。

Atlas 支持多种数据来源：

#### 自动采集

- IPMI
- Redfish
- SNMP
- `nvidia-smi`
- `lspci`
- `ethtool`

#### 其他来源

- 人工录入
- 文档导入
- 厂商数据
- 客户反馈数据

Atlas 不假设所有设备都可以实时采集，也不以持续采集作为资产存在的前提。

数据来源示例：

```yaml
Source:
  type: CUSTOMER_REPORT
  access: NO_DIRECT_ACCESS
  update_frequency: MONTHLY
```

对于内部测试环境，可通过 Redfish、IPMI、`nvidia-smi` 等方式实时更新；对于客户环境，则可能只能依赖客户报告、文档或人工录入。

### 6.5 History Model

描述“过去发生了什么”，记录：

- 状态变化
- 部件更换
- 位置变化
- 参数变化
- 运维记录

例如 GPU 的位置历史：

| 时间 | 事件 | 位置 |
| --- | --- | --- |
| 2026-01 | 安装于 | GB300-001 |
| 2026-08 | 更换到 | GB300-002 |

## 7. 业务领域

Atlas 在 Core 基础上提供业务能力，并通过平台能力支撑跨客户、跨地点的资产运营。

### 7.1 Asset Domain：资产管理域

负责：

- 采购
- 验收
- 入库
- 出库
- 调拨
- 资产编号
- 供应商
- 维保
- 生命周期

### 7.2 Operations Domain：运维管理域

负责：

- 工单
- 巡检
- 维修
- 故障
- 变更
- 维护记录

### 7.3 Knowledge Domain：知识管理域

负责：

- 设备与故障知识
- 维修经验
- 操作手册
- 客户交付资料
- 维保知识沉淀

### 7.4 Workflow 能力

Workflow 是平台能力，不是一级业务域，负责支撑：

- 采购与验收审批
- 资产交付
- 客户反馈处理
- 现场维修
- 部件更换
- 变更与审计

### 7.5 Automation 后续扩展能力

自动化能力基于 Atlas 基础设施模型提供，后续可扩展：

- PXE 部署
- 硬件发现
- Firmware 管理
- 自动验证
- 批量操作

## 8. MVP 版本规划

### 8.1 Atlas Core MVP

目标：建立基础设施数字模型。

- 对象管理：创建对象、查询对象、修改对象
- 关系管理：对象关联、拓扑查询
- 属性管理：技术规格、扩展字段
- 数据来源：手工、导入、自动采集
- 历史记录：状态变化、属性变化

### 8.2 Atlas Asset MVP

基于 Core 实现：

- 采购申请
- 审批
- 到货
- 验收
- 入库
- 出库
- 生命周期管理

### 8.3 Atlas Ops MVP

- 运维工单
- 巡检
- 维修
- 变更

### 8.4 Atlas Automation MVP

自动化不属于当前一级 MVP 业务域。后续可基于 Core、Data Source 和 Management Scope 实现：

- PXE
- DHCP
- 硬件采集
- 自动验证

### 8.5 多客户与现场运维场景

MVP 需要支持：

- 多租户和多客户隔离
- 资产所有权与使用权分离
- 客户站点和部署位置管理
- 管理权限范围
- 客户报告、文档和人工录入等非实时数据源
- 现场维修、部件更换和维保记录

## 13. 开发原则

### 数据优先

基础设施数据是所有能力的基础。

### 模型优先

先设计对象和关系，再开发业务。

### 生命周期优先

所有资源都有生命周期。

### 简单可靠

避免过早复杂化。

### AI 辅助开发

利用 ChatGPT、Codex 提升研发效率。
